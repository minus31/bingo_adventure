현재 구조의 예상 오류 요소

코드는 변경하지 않고 정적 검토와 격리된 실제 Blob 동시 요청으로 확인했습니다.

치명적

PIN과 관리자 권한이 브라우저에만 존재

팀 PIN, 관리자 PIN, 로그인 상태는 클라이언트 코드와 Web Storage에만 있습니다. API에는 인증 검사가 없어서 직접 POST하면 다른 팀 배치, 판정, 전체 초기화를 수행할 수 있습니다.

치명적

영상 업로드 토큰도 팀 인증 없이 발급 가능

teamId와 catalogId 형식만 맞으면 업로드 토큰을 요청할 수 있습니다. 사용량 남용, 임의 팀 경로 업로드, 저장 비용 증가 가능성이 있습니다.

높음

팀 완성 후 동시 요청에서 ETag 충돌

완성된 team JSON을 같은 경로에 여러 요청이 동시에 덮어쓰면서 500이 발생할 수 있습니다. 실제 burst 테스트에서 Precondition failed, ETag mismatch를 재현했습니다.

높음

이벤트 파일 직후 읽기가 실패하면 snapshot에서 누락

event 읽기 오류를 건별로 무시하기 때문에 새 이벤트 일부가 최신 snapshot에 들어가지 않을 수 있습니다. 다음 상태 변경이 발생해야 전체 events를 다시 읽으며 회복될 가능성이 있습니다.

높음

낙관적 저장 실패가 사용자에게 표시되지 않음

화면은 먼저 성공한 것처럼 바뀌고 POST 실패는 조용히 무시됩니다. 재시도와 로컬 영속화가 없어 같은 탭에서는 저장된 것처럼 보이고, 새로고침하면 사라질 수 있습니다.

높음

영상 업로드와 제출 등록이 분리됨

video 업로드 후 submit 이벤트 저장이 실패하면 Blob에는 영상만 남습니다. 반대로 UI는 addSubmission 완료를 기다리지 않고 제출 완료 화면을 보여줄 수 있습니다.

높음

10초 제한은 브라우저에서만 확인

서버 토큰은 MIME과 15MB만 제한합니다. API를 직접 사용하면 10초가 넘는 영상도 업로드할 수 있습니다.

중간

영상 수와 총용량에 상한이 없음

같은 팀이 같은 과제에 여러 번 제출할 수 있습니다. 72개를 각 15MB로 한 번씩만 올려도 약 1,080MB이며, 재도전과 고아 영상은 여기에 추가됩니다.

중간

공개 Blob에 영상과 team JSON 저장

영상 URL을 알면 인증 없이 재생할 수 있고, team JSON 경로는 예측 가능합니다. 행사 영상의 공개 범위를 사전에 합의할 필요가 있습니다.

중간

클라이언트가 제출 시각과 영상 URL을 지정

유효한 날짜라면 제출 시각을 그대로 수용하며, 허용 URL도 현재 저장소로 제한하지 않습니다. 직접 API 호출로 최초 제출 순서와 참조 영상을 조작할 수 있습니다.

중간

자정에 게임이 자동으로 새 날짜로 전환

Asia/Seoul 00:00 이후 API는 새 폴더를 사용합니다. 자정을 넘겨 진행하면 기존 상태가 사라진 것처럼 보이며 전날 영상과 JSON은 그대로 남습니다.

중간

이벤트 증가에 따라 저장 작업이 점점 무거워짐

상태 변경마다 모든 event를 다시 읽고 전체 snapshot을 새로 저장합니다. 누적 event 읽기는 N(N+1)/2 형태로 증가하고 snapshots 총용량도 비슷한 방향으로 커집니다.

동시 사용자 검증 결과

운영 데이터와 분리된 Blob 경로에서 실행했습니다.

기본 동시 접속, 통과

빈 게임 8개 동시 GET, 서로 다른 과제 4개 동시 배치, 이후 6개 병렬 조회가 모두 HTTP 200이고 동일한 상태였습니다.

재시작 복구, 통과

서버 재시작 후 4개 병렬 GET에서 저장된 5개 과제가 동일하게 복구됐습니다.

완성 팀 이후 burst, 실패

A팀 18칸 완성 뒤 B팀 10개, C팀 18개를 각각 동시에 요청하자 ETag mismatch 500이 반복됐고 최종 snapshot에서 C팀은 13개만 보였습니다.

실제 사람의 터치 간격은 burst 테스트보다 느리므로 발생 빈도는 낮아질 수 있습니다. 다만 여러 폰이 같은 팀을 채우거나 네 팀이 동시에 제출하는 순간에는 동일한 충돌 경로를 사용할 수 있습니다.
